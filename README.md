# AgentLab Interview V0.2

本地单用户 Agent 工程实操训练：选题 → 编辑 → 保存快照 → Docker 真实行为测试 → 逐级提示 → 提交新评测 → 查看证据报告 → 刷新恢复。

当前新建生成使用 `fault-first-v1`、`case-impact-v1` 与 `lean-generation-v1`：先验收故障，再生成修复。规范审核及覆盖复查直接围绕原始需求和行为测试，不再要求覆盖 DSL、清单纠正或重复采纳审查。故障阶段逐场景审核影响字段，完整保留其他字段；正常/修复版仍须满足全部正确期望。无效候选先进行一次受控复核，复核后仍失败则停止该重复路径并保留具体要求与执行证据。新规则不迁移历史实例。详细流程见 [FAULT_FIRST.md](docs/FAULT_FIRST.md)，本文后部旧策略说明仅适用于相应历史版本。真实模型重放仍可能失败，不承诺生成率提升。

新任务另带 `inventory-correction-v2`：清单规则错误会向评测 Agent 返回原候选和具体缺项，在原总预算内最多两次纠正。整个清单缺失/为空时可受限补齐，已有清单继续局部修改，补齐条目仍须完整来源与规则校验。覆盖评测提出接口缺失时，`interface-review-v2` 要求独立复核具体证据，并逐规则记录判断与处理；可同时修规则和补测试，未处理问题须说明具体原因。只有批准明确字段后才能交给构建提交受限补丁，构建也可引用公开依据退回。局部合并仍须完整审核，不自动改期望或放宽覆盖。历史记录不自动升级。

V0.2 新增需求驱动的分阶段项目生成、独立结构化评测和审核发布流程。实际验证与失败记录见 [VERIFICATION.md](VERIFICATION.md)；Docker 权限步骤见 [DOCKER_SETUP.md](docs/DOCKER_SETUP.md)。原四道固定任务与历史记录继续保留。真实权限边界实例已获用户对固定摘要的明确批准，作为本地内部试用题发布；已完成故障执行、参考修复、真实模型对话/反馈与报告刷新闭环。这是系统功能验证，不代表学习效果或真实工具安全能力。

## 前置条件与启动

- Linux/macOS 上的 Python 3.10+、Node.js 22.12+、npm。
- 可运行 Linux 容器的 Docker Engine / Docker Desktop，当前用户可执行 `docker info`。
- 初始化需要联网安装依赖、拉取 Python 基础镜像；训练时容器无网络。

```bash
cp .env.example .env
./scripts/init.sh
./scripts/start.sh
```

访问 http://127.0.0.1:5173 。后端为 http://127.0.0.1:8000 ，API 文档 `/docs`。不需要模型密钥，默认 **MOCK · 确定性辅导**。停止时 Ctrl+C；SQLite、会话和代码保存在 `data/`。不要使用多 worker 启动后端：本版是单进程服务，内部限同时两次执行。

如果没有 Docker，可先安装应用依赖并体验编辑、保存、逐级提示与 mock 对话；**测试与提交禁用**：

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
npm --prefix frontend ci
./scripts/start.sh
```

Docker 就绪后构建镜像并点击界面“重新检查”：

```bash
docker build -t agentlab-runner:0.1 -f backend/Dockerfile .
```

## 三个板块

- **题库**（默认 `/library`）：四道固定任务及已审核发布的生成任务。进入任务后保存全部文件、运行公开测试、请求提示、提交并查看快照证据报告。
- **故障题目生成**（`/generate`）：输入需求，点击“开始生成项目（调用模型）”。新实例先生成公开规范和故障项目；独立评测审核并生成检查，Docker故障验收通过后冻结，再生成局部修复补丁、验收修复版和规避版本。新任务不再要求确认技术契约，只有训练目标确有歧义时才询问用户。Docker 验证与教学材料完成后，作者打开私有审核资产，逐项核对契约和期望值，记录依据后发布。失败实例不会进入题库。
- **个人工程项目训练**（`/projects`）：尚未开放，仅说明未来方向，没有仓库导入或训练后端。

深链接、刷新和浏览器前进后退均可用；需求草稿与各会话未保存的多文件草稿分别保存在本机浏览器，服务端生成不随切换页面取消。已发布任务的新训练使用冻结资产，不重新生成。

生成支持小型 Python 标准库项目、2–5 个业务模块、一次 `scenario(data)` 调用内完成本地场景。需求领域开放，生成入口明确限定本地模拟；用户明确要求真实外部系统时应提示不支持或澄清，不静默替换；真实模型推理质量不能由固定模拟输出证明。无密钥时生成页使用显著标记的 **MOCK 固定样例**，只验证工程流程。

新任务使用 `fault-first-v1`（保留直接构建入口），旧记录继续 `direct-build-v1` 流程，每批最多24次模型请求、96000输出记账Token、600000输入字节、1200秒活动时间与10轮实际验证。合并构建单次上限12000输出Token，沿用适配器上限。失败按证据自动回到构建、评测或规范补齐阶段，预算耗尽后需明确点击“重新生成（消耗Token）”授权新批次。规范补齐只允许改独立审查指出的字段，并使下游资产重新验证。重启不自动重发模型请求；旧生成记录继续原来的契约确认流程。完整协议见 [生成资产格式](docs/GENERATION_FORMAT.md)。

自动门禁通过仍需作者审核：模型生成的期望值不是天然正确的标准。作者页面包含答案，和训练页面分离；本地所有者仍可检查私有源码。本版不承诺防范本机所有者。

## 真实模型

修改 `.env` 后重启：

```dotenv
AGENT_MODE=real
MODEL_BASE_URL=https://your-provider.example/v1
MODEL_NAME=your-tool-capable-model
MODEL_API_KEY=your-local-secret
```

适配器实际发送兼容 Chat Completions 的 HTTP 请求，要求供应商支持 `tools`/`tool_calls`。地址填 API 根路径，程序追加 `/chat/completions`；密钥仅后端持有。只发送允许的已保存文件、题面、可见证据和用户说明，不发送隐藏测试、参考修复与系统配置。模型不可用时明确显示错误，客观评测不受影响。已使用本机真实配置验证工具往返与报告持久化，详见验证记录。启动脚本负责加载 `.env`；直接启动 uvicorn 时须自行导出配置。聊天输出预算为 4096 token（含推理），每次 HTTP 请求超时 60 秒；每轮最多 4 次模型请求、6 次工具调用，最后一次请求保留给无工具总结。报告独立请求三条短反馈：首轮 1200 token，只有 output_limit 可自动重试一次（1800 token），合计上限 3000；单次等待最多 40 秒，总预算 90 秒。对官方 DeepSeek API 的 deepseek-v4-* 报告请求显式设置 thinking.type=disabled；其他供应商不猜测专有参数。每次尝试保存脱敏请求/响应元数据，缺失用量记为未知。报告显示生成中、已生成或失败类别；服务重启会将未完成反馈标记为中断。不会存储模型隐藏推理。

官方 DeepSeek 的生成调用可单独设置 `GENERATION_THINKING=enabled` 和 `GENERATION_REASONING_EFFORT=high`（支持 low/high/max），默认仍关闭。推理与正文共同受原有角色输出额度约束，不保存隐藏推理。角色协调器使用 `GENERATION_REQUEST_TIMEOUT`（默认90秒，可设30～300秒），另有最多10秒协调等待，始终受整批剩余时间约束；这不会改变聊天或报告预算。调用记录区分请求模型与供应商返回的 `response_model`，缺失字段不猜测。DeepSeek 模型别名可能调整或转发，不能仅凭名称认定底层模型已更换或生成率提高。

需要更高推理额度时，可为新生成批次设置 `GENERATION_OUTPUT_MULTIPLIER=2`～`4`（默认1）：按倍率提高阶段输出上限和整批默认输出额度，最多分别为48000与384000 token。倍率保存到批次预算中；旧批次未记录倍率时按1处理，后续修改环境默认值不会放大旧预算。总请求数、总时长及所有验证门禁不变；报告和聊天额度不受影响。

## 使用

1. 选择三道基础任务或进阶任务“知识库更新后的旧版本污染”。每次开始创建独立工作副本。
2. 阅读症状与约束，查看只读公开 pytest 和固定 JSON 输入；在本地 Monaco 编辑器修改任务允许的文件。基础任务编辑 `solution.py`；进阶任务可切换五个业务模块，统一入口只读。
3. 填写诊断说明。未保存状态明确显示，草稿保存在浏览器 localStorage，刷新可恢复；“保存”一次保存全部可编辑文件（包括未选中的文件），写入 SQLite / 工作区。
4. “保存并运行公开测试”先保存，然后创建不可变内容寻址快照。运行面板轮询持久化状态，显示检查、错误、超时、退出码、耗时与执行 ID。
5. 向 Agent 描述观察，或点击“请求提示”逐级开放 L1–L3。每次成功获取记录时间和等级；L3 后显示“已获取全部提示”，按钮禁用，接口拒绝追加，不再增加次数。历史报告仍使用提交时的提示记录。
6. “保存并提交评测”重新运行公开与隐藏检查，不复用旧通过结果。报告展示提交时诊断、提示记录、检查与代码快照；可点击查看提交代码、定位执行证据。
7. 点击左上角回任务列表，查看历史；重新打开训练或刷新恢复。

### 多角色生成与自动修复（roles-v1）

当前新记录在roles-v1预算协调器上启用direct-build-v1：合并规范设计与项目构建，保留独立评测、失败诊断和教学上下文。旧记录仍使用独立契约阶段。学习者辅导仍是原来的单 Agent。生成验证失败后自动诊断并限定修复资产，再运行完整 Docker 矩阵；不会因为第一次失败就结束，也不会自动发布。

- 默认每批最多 24 次模型请求、96000 输出 token 记账额度、600000 UTF-8 输入字节、1200 秒活动执行和 10 轮验证。等待作者确认不计活动时间；缺失供应商 usage 时按本次完整预留保守记账，不代表精确费用。
- 环境或凭据不可用时暂停；新记录规范缺项由独立审查退回构建补齐，只有用户训练目标歧义才等待用户澄清。不能通过改测试期望迎合实现、接受假规避或改为宿主执行来提高通过率。
- 页面显示当前角色、修复轮次、预算及失败记录。**重新生成（消耗Token）**展开恢复选项：中断可使用剩余预算继续；新增预算必须勾选明确授权，创建关联原记录的新批次。旧失败记录和已发布实例不变。
- 作者审核区提供完整私有诊断及版本记录；不进入题库公开资产或训练 Agent。运行中的取消阻止后续阶段，已发出的供应商请求仍可能计费。
- 旧策略记录继续可读；重新尝试旧失败记录需明确新批次预算。已发布任务只能创建新版本，不能原地重生成。

可执行验收：`./scripts/acceptance.sh`。新增 `tests/test_generation_flow.py` 覆盖预算、权限、自动修复与实际 Docker；浏览器测试覆盖耗尽后新批次确认和恢复。真实模型试验是单独的 opt-in `scripts/roles_probe.py`，不自动发布，实际成功/失败见 `VERIFICATION.md`。

### 旧生成记录：契约歧义与需求歧义

以下是旧记录兼容流程；新记录由合并构建与spec_review处理。旧记录生成过程中发现歧义时，契约 Agent 先独立对照原始需求和平台公开约定：

- 需求已经明确、只是契约误述或遗漏：提出最多4个局部字段补丁，列出旧值、新值和原文依据。程序校验路径、旧值、依据及完整契约；独立模型校核通过后自动保存新契约版本，重新构建项目、生成独立检查并实际验证。
- 用户需求本身有多种合理解释：页面显示“需要你明确需求”，提供具体问题、选项与说明输入。答案草稿支持刷新恢复；提交后用当前批次剩余预算继续，不重新填写整份需求。
- 契约明确、问题在实现或评测：保留契约，回到对应角色；错误期望只有经过独立契约核对后，才能由不读取实现输出的评测角色针对指定检查重新推导。

没有自动覆盖已发布任务或旧证据。即使模型称为“文字调整”，当前实现仍保守地废弃下游验证并重验，不能靠这一标签跳过执行。独立校核不等于语义正确性的数学证明，发布前人工审核仍然保留。

### 生成状态、成本与作者审核

保留成本与进度展示、作者审核摘要。供应商实际返回的用量与平台预算记账分开，缺失用量标为未知。作者可查看需求、约束、故障说明、参考改动、实际执行结果、范围和批准绑定；私有资产不进入学习者上下文。

按用户要求，七项优化中的前五项已回退：不再自动建立失败回归档案，不使用新增的证据充分性强制路由，不按无进展提前终止或复用矩阵，不新增反例门禁，不要求六维契约校核。当时恢复既有的有界角色修复、独立契约校核与六项执行门禁；后续separated-evidence-v2与direct-build-v1更新见上文和下文。

已有 `data/generation-regressions/` 私有档案、历史矩阵和报告保留，不迁移、不删除；旧进展和扩展校核记录只读展示。历史 `no_progress` 记录可通过“重新生成（消耗Token）”选择恢复当前批次剩余预算，不会自动发起调用。更早的契约局部修订、用户需求澄清、固定快照与人工发布批准仍保留。

## 生成纠错协议更新

新建生成记录使用 `separated-evidence-v2`：独立评测只生成正确行为检查；另一个有界模型阶段根据已经冻结的私有故障设计生成结构化故障断言，不读取实现或实际输出。生成页显示“故障复现检查 Agent”。断言与代码、检查一起绑定验证矩阵和审核摘要，仍需作者人工审核。

评测修复采用带资产哈希和准确旧值的字段补丁：分类、正确期望、补覆盖分别授权，不能夹带修改或追加检查。同一已明确契约的期望核对不会再次进入相同契约审核。阶段记录区分模型服务错误、响应格式错误、诊断拒绝和补丁拒绝；“资产校验通过”不等于最终验收通过。

旧生成记录和已发布任务继续使用原协议，历史资产不迁移；新协议不会自动重试旧失败记录或发布新题。规避生成与自然语言语义判断仍可能失败，预算耗尽仍会保留证据。真实联调结果及限制见 VERIFICATION.md。

生成纠错现会明确指出缺失的行为覆盖，评测能参考自己上一次被拒绝的候选；首次执行前连续两次资产校验失败会回到独立规范审查，区分补检查和补规范。新合并流程的检查做两次独立Docker执行，提供有限一致性证据，避免只补覆盖标签就宣称验证确定性；会增加执行开销，但预算上限不变，旧已发布题不迁移。

## 当前生成角色：consolidated-v1

新建任务使用三个角色：**项目构建 Agent**负责规范设计、各版本构建和指定版本修复；**评测 Agent**负责规范审查、独立行为测试、故障复现检查和执行失败分析；**教学 Agent**在实际验证通过后生成教学材料。角色合并不取消阶段：每阶段重新构造上下文，不传递完整聊天历史。只有行为测试阶段是对实现盲测；失败分析明确可以看实现和实际结果。

项目修复接收程序生成的工单：正常/参考版满足正确行为，故障版保留冻结主要故障，规避版保留应被检查拒绝的错误。自由文本解释不能扩展修改权限。阶段记录显示角色名、阶段及role_id；旧记录保留原角色记录和策略，不自动重试。训练辅导、报告反馈、预算、Docker隔离和人工发布审核保持原样。合并不保证生成成功，真实结果见VERIFICATION.md。

生成修复现使用版本化工单（新任务及明确授权的新预算批次）：代码修改、检查分类、故障指纹、规范复核、补证据请求为互斥动作。构建阶段可以返回明确的约束冲突或证据缺项；下一轮必须回应冲突。相同证据下重复冲突/重复拒绝，或候选执行仍无变化时，页面显示“交接冲突待人工复核”，不会继续耗完模型预算。作者审核中可查看冲突双方、候选状态和执行绑定；旧记录保持原版本语义。

修复代码和评测先保存为候选，完整 Docker 门禁通过且资产摘要一致后才接受。检查分类修改必须经过评测阶段按冻结故障范围复核，不修改输入或正确期望。工单格式合规不代表修法正确，自动验证通过也不替代人工发布审核。

生成请求默认 `GENERATION_JSON_MODE=auto`：官方 DeepSeek 使用 `json_object`，其他地址保持提示词约束并在调用元数据记录。可对已确认支持的供应商设置 `json_object`，或显式设置 `prompt`；不自动降级重发付费请求。JSON模式不保证字段或项目正确。构建语法/结构失败会携带原响应定点纠正，最多两次且计入原总预算；资产约束错误走原设计修复流程。错误分类、原始调用和格式修复关联保留供作者审计。

诊断提出缺证据时，平台现在先查找当前版本文件及匹配快照的检查结果，再将具名证据交回诊断。必要时可对当前独立评测已有场景做 Docker 诊断实验；每个矩阵最多两轮证据补充、两次新实验，计入原预算。实验仅记录观察，不评分、不新增测试。暂不执行内部函数、任意命令或模型新拟输入。作者可查看完整证据与绑定，学习者和初次独立评测不会收到这些私有材料。

新建生成任务使用冻结故障触发规则：系统先固定故障输入范围，再计算目标/正常回归分类，并独立审核故障影响及实际执行。这可避免把“空工具”“排序”等检查主题误当作未触发故障的证据。规则仅支持有界 JSON 条件，不能表达的机制仍需人工核对；不保证任意需求都能生成。已有生成记录继续使用原协议，若要验证新流程请新建生成任务。详见 [资产格式](docs/GENERATION_FORMAT.md) 和 [架构说明](ARCHITECTURE.md)。

规范补齐（`fault-model-v1`）：仅返回独立审查授权字段的局部补丁，服务器保留冻结项目、故障规则与私有描述。每次审查最多3次调用（首次加2次纠正），每批最多6次补齐调用，仍受总预算限制。具体字段错误会反馈给同一构建阶段；冻结依据矛盾或次数耗尽显示“规范补齐待复核”，不会自动无限重试。旧任务协议保持兼容。

新流程具体步骤、证据交接、修改权限和限制见 [先故障后修复方案](docs/FAULT_FIRST.md)。生成详情分别显示故障/修复验收进度，作者审核可在完整版本生成前查看故障候选。


新建故障优先任务还会核对原需求覆盖：规范审核固定带用户原文引述的需求清单，独立评测后检查真实输入/正确期望能否见证各项需求。共享状态必须在同一场景中体现多个实体，中断要求必须观察中间状态；仅写覆盖标签不够。接口缺项退回项目构建，测试缺项只追加场景。该检查不替代 Docker 执行或作者审核，历史记录不强制迁移。

新建生成另带 `stage-recovery-v1`：规范、独立评测与覆盖审核等准备阶段的不同错误可在总预算内继续纠正，每个绑定版本最多六次；相同候选和相同校验错误重复时停止。原候选、具体缺项及纠正次数进入同阶段的实际请求。清单局部纠正仍使用原两次上限，代码/执行阶段不扩大修订权限。疑似用户需求歧义先经过独立公开规范复核与校核；若明确需求与生成规范冲突，则由构建阶段修改授权字段，不直接要求用户重新澄清。

隔离开发重放可显式使用 `BudgetPolicy.development()`：64 次请求、1536000 输出预算、2400000 输入字节、7200 秒活动时间、30 次验证、阶段输出倍率 4。普通新任务默认预算和历史批次预算保持原值；提高预算不代表取消门禁或自动发布。

新建任务还支持 `inventory-review-v1` 清单质疑复核：覆盖审核只能提出带原需求引用、规则下标和证据的质疑；清单复核使用独立上下文，接受时只改被质疑项的规则，驳回时原样保留清单，并将理由交回覆盖审核。每次仍重新验证覆盖，不将复核意见算作执行通过，历史任务不自动升级。

历史 `adoption-coverage-v1` 任务继续使用以下协议（新建默认已改为精简流程）：补测仅提交新增用例，程序保留旧测试；公开规范和清单纠正先经独立的正常标准采纳审查，防止把故障症状写成正确期望；覆盖复核提出的缺口需明确处理后才能推进。拒绝会将具体理由交回对应阶段，仍受总预算和局部修复上限约束。历史生成任务保留原协议，自动通过仍不代表题目已获人工认可。

生成纠正补齐（executable-corrections-v1）：重新启动后端后，新建生成记录启用服务器绑定的采纳审查、按具体任务计数的纠正、未批准非法清单 ID 改名，以及故障复核到追加测试的入口。历史记录沿用原协议；独立验证副本的重放结果不等于题目已生成或已发布，具体执行与限制见 VERIFICATION.md。
