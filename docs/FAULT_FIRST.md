# 先故障、后修复：fault-first-v1 / case-impact-v1

## 具体流程与修改权限

1. 项目构建：输出任务规范、完整故障业务模块、私有主要故障要求和主要症状字段。禁止正常版、修复版和规避版本进入首次输出。
2. 可验证性审核：只读用户需求与公开规范，沿用独立输出字段依据审核。规范缺项只可改获准公开字段，不能顺带改故障源码、私有设计或主要症状字段；真正需求歧义才询问用户。
3. 独立评测：只读公开规范和接口。生成正确期望、目标与回归、公开与隐藏、行为覆盖及规避要求，不看实现、私有故障说明或实际输出。
4. 故障复现及影响审核：独立上下文只读规范、私有设计和全部固定测试，不读实现或实际输出。逐场景列出确实不同的字段和错误值，其他字段由程序保留正确期望。主要公开/隐藏复现只选择路径，由程序复用影响表中的错误值，不生成第二套断言；来源用ID定位。无差异边界不强行制造故障。错误与正常无法区分退回未冻结设计；公开规则不足以支持精确期望先回独立规范审核，不反转错误值凑差异。
5. 故障验收：受限Docker中每场景重复两次。主要目标须命中错误，完整回归全部正确；受影响场景逐字段检查故障断言和未受影响字段。阶段验收、最终矩阵与模型交接使用同一要求编译器。语法/超时/协议错误不算复现；通过后才冻结。校正故障代码与修改影响审核有不同权限，不由一条失败自动决定必须改代码。
6. 冻结：保存完整故障验收矩阵、环境镜像ID、故障代码、规范、评测和复现检查摘要。只有完整且通过的实际矩阵能冻结。
7. 修复补丁：绑定冻结故障摘要，精确before/after替换，最多涉及两个允许业务模块，不接受任意路径、shell或完整正常项目。每次尝试均相对同一冻结故障基线；服务端应用并保留Python缩进，按既有Project格式规范化代码字节。
8. 修复验收：全部正确检查通过、故障消失且重复稳定，沿用冻结镜像。失败只生成新的修复补丁，不改故障基线、检查或诊断要求。
9. 规避生成与最终验证：基于规范和已通过修复生成2–3种错误修复，复用原全版本Docker矩阵；正常版与参考修复均由已验收修复快照重建。禁止为增加源码差异另写一份未经验收的正常版。规避不合格只重做规避；最终基线不一致或环境变化须复核/恢复环境。
10. 教学、审核、发布：最终矩阵通过后才生成材料。审核摘要包含各阶段资产、补丁、验收证据与最终矩阵；人工批准仍必须绑定该摘要。自动化mock审核发布不计真实人工批准。

## 交接规范

`repair_requirements`由程序从当前矩阵、独立检查和故障断言生成逐场景义务：check_id、case_id、input、objective、state、required_assertions、actual、error、stable。state区分unmet与must_preserve。故障目标只携带指定错误断言，避免在同一目标旁同时给出相反的正常期望。其他回归/修复才要求正确expected。已满足目标不会因为不出现在失败列表中而丢失。字段/基线摘要/路径错误返回具体field、received、required或allowed、动作建议；反馈记录后直接进入同阶段下一次适配器请求。条件不能兼容时由模型指出冲突检查，程序不猜测改规范或翻转方向。

故障构造校正和消除故障分别使用fault_correct/fix_patch阶段及不同schema上下文，不再让诊断自由文字决定版本目标。程序决定修改权限与门禁，模型仍负责代码修改和语义判断；校验不能保证模型一定遵从。

## 预算、恢复与兼容

继续使用每批24次模型请求、96000输出Token记账、600000输入字节、1200秒活动时间和10次验证。新增阶段单次上限：fault_correct/fix_patch 6000、evasions 10000；原project_build上限12000。字段/格式错误只允许一次定点纠正；首次无变化/回摆/重复观察转一次逻辑复核，复核本身可纠正一次格式，之后最多一个代码候选，再失败停止本分支；未冻结设计重建每批一次，公开规范补齐最多两轮，Amendment沿用每轮三次/每批六次上限，均不突破原总预算。不可用环境、供应商配置错误、模型明确设计冲突有独立暂停状态。不会无限循环。已保存成功模型资产可从检查点继续；不完整执行不能当成通过。重启不自动重发付费请求。明确授权新批次时复制资产，父记录不变，幂等键避免重复请求。

仅新API创建实例启用。旧direct-build/fault-model/contract-confirmation实例和旧四道题继续原流程。发布后的工作区、快照、执行器、提示、报告仍沿用既有实现。新流程不采用旧的输入谓词DSL。独立评测的group是初步建议，最终故障阶段与发布的分类由已审核的逐场景差异确定；独立输入与正确期望不会因分类改变而修改。未带case-impact-v1的历史故障优先记录继续旧规则。

## 信任边界与限制

源码仅在原受限Docker运行，宿主只解析AST、复制字节和比较结构化输出；测试依然是数据，不执行模型评测代码。独立评测不因实现失败调整期望。本流程作者/构建修复上下文可以接收必要的阶段测试证据（包括失败固定场景）；初始独立评测保持盲测，训练Agent只接触公开任务资产和公开执行结果。作者资产不进入训练聊天。

正常版先通过不是此流程的前提：其正常/参考基线是修复验收后的产物。通过只证明有限测试，不能证明不存在额外故障或覆盖所有边界。需求语义、私有设计、主要字段选择、目标/回归分类仍可能错误。真实案例的成功与失败必须分别记录，不承诺生成率提高。

## 修订、交接与终止证据

`generation_fault_obligations`统一生成requirement_id、input、required_assertions、actual、state和execution_observed。故障阶段同一场景可以同时有`:fault`与`:preserve`，保护不同字段；完整修复为`:correct`。不再因为一个标为regression的场景失败就强制修代码；应先核对主要机制是否自然影响该字段。数组整体比较，不接受任意表达式。

case-impact-v1构建使用ReviewedFaultBundle，与影响审核共用schema叶路径：对象按公开字段逐叶引用，数组整体为叶值，根数组/标量路径为[]。数组下标、通配符、JSONPath表达式、非空对象父路径及重复症状路径在接受项目资产前被拒绝，具体合法路径进入下一次构建请求。独立影响审核与失败复核均收到服务端path_policy，包括schema_leaf_paths及各case的allowed_impact_paths/allowed_primary_paths；它只从公开schema、固定症状和独立正确expected的形状计算，不读取执行结果。错误断言仍需符合类型、区别于正确值，未受影响字段继续保留。

带case-impact-v1的旧资产若存在不兼容症状路径，指纹调用前即停止并明确要求显式新版本修订；不会静默截短路径、覆盖历史资产或重复付费审核。未启用case-impact-v1的旧协议保留原解析方式。合法父数组断言只是结构规则，不保证模型判断正确；自由文字建议不构成授权，后续资产仍须程序校验。

公开规则缺项先交独立spec_review，仅传公开来源原文；获准后复用既有Amendment局部补丁，程序复制最新代码和私有设计，避免重写整包导致冻结资产漂移。新规范失效旧评测、影响、矩阵和教学。未冻结设计问题有独立design_rebuild入口，保留用户目标和设计历史；只有真实需求歧义才问用户。已冻结后不原地改标准。

冲突须指出两个真实requirement_id及不能按合法条件同时满足的原因；引用正确不证明语义正确。失败复核可读代码/结果，重新进入影响审核时移除复核自由文本，只传问题类型、场景ID和来源ID，保持阶段隔离。复核的allowed_decisions由程序提供，没有已执行未满足要求时不能要求改代码。

终止时error摘要列出仍失败的门禁与具体requirement_id，私有`recovery_stop`保存完整输入、字段目标、实际值、执行ID和复核指令。计数及AST/观察摘要持久化，重启和普通恢复不能清零；明确授权新预算会创建子记录。补丁通过结构校验不等于执行正确，单次真实重放成功或失败不证明生成率。精确历史回归资产在tests/fixtures/fault_first，仅供服务端测试/作者审计，不属于学习者包。


## 原需求覆盖门禁（demand-coverage-v1）

新建API任务：构建 → 规范审核并固定原需求清单 → 独立评测 → 原需求覆盖复核 → 故障影响/复现审核 → Docker故障验收 → 原有冻结、修复及发布流程。旧记录不插入新阶段。

覆盖复核保持独立上下文，不看实现或实际输出。服务端检查引用、数据关系与摘要绑定；多个独立case不能拼成共享存储证据，完成输出不能替代中断状态。缺接口回构建，缺原需求清单回规范审核，缺场景仅追加测试。旧case及其正确期望完全不变；审核自由文字不是新增验收要求。每类最多两次修订，仍受整批预算约束。恢复已保存的复核直接应用检查点，不重发模型。执行和发布均重新校验批准绑定；规范、清单或测试变化使旧批准失效。

原需求抽取、证据规则及语义评审仍可能有遗漏或误判；程序能拒绝不存在的路径和不符合数据条件的覆盖声明，不能证明全需求完备或LLM判断正确。必须保留实际Docker验证及作者审核。

## 清单局部纠正（inventory-correction-v1）

仅新建需求覆盖任务附带此标记；历史记录不迁移，旧规则执行含义不变。仍由评测Agent负责清单，不增加Agent或必经阶段。`length_eq`检查每个选中值自身长度（数组元素数、对象键数、字符串Unicode码点数），不是匹配数量；对`*/id`选中的数字求长度会被拒绝。关系规则`distinct/equal`的minimum下限2同时进入新任务的模型schema。单实体重试不等同多实体隔离；运行限制及排除范围不硬编成输出证据。

清单错误保留原候选、逐字段诊断、原需求、公开规范、上次尝试及剩余预算。能独立检查的缺项汇总反馈，无法检查的部分明确标记，不宣称其已通过。独立输出规则本身不合格时仍走原规范纠正，不把局部清单补丁当作完整审核批准。

局部纠正使用`Correction`：`binding`固定contract/source/candidate摘要；`decision=patch`只提交`replacements`（原ID的完整需求项），其余项和原output_rules由程序复制；不允许添加、删除需求或改写有效原文引用。合并候选重新经过完整清单与公开规则校验。`decision=revise`只给具体issues；接口缺项的interface_gap=true走已有构建重建，取值规则缺项走已有规范补齐。构建后受影响资产照常失效，旧审核与历史候选保留。

每批最多两次局部纠正，消耗原24请求/时间/Token预算；出现不同错误可继续，不按同阶段第二次失败立即结束。失败但有变化的候选成为下一轮纠正依据，原样候选复用原拒绝事实；两次后仍未通过则保留具体未解问题停止。重启、普通恢复及接口修订不清零此计数。新标记不更改Docker、行为门禁、报告、提示或发布批准要求。

初审与覆盖复核共同接收同一rule_policy，运行约束不因未列入行为清单而成为遗漏；此阶段无实现/执行证据，不能据此宣称代码依赖或持久化路径已验证。实际文件读写与关闭重开行为仍需测试。既有义务的ID/原文/类别以原需求摘要仍匹配的已接受清单为准，不能锁住被拒候选的漂移引文而阻止恢复；所有可确定的漂移和required值一并反馈。

候选擅自改名时，patch可用restore_ids显式列candidate_id/accepted_id，并在replacements提供恢复后的完整项。只能把未接受的候选ID恢复为同一原需求下已接受、当前缺失的ID；禁止覆盖已接受项、任意新ID、重复映射和缺少替换项。数量及其他项保持不变，服务端不猜对应关系；合并后原文、类别及完整审核照常校验。

## 有界恢复策略（bounded-recovery-v1）

新建 API 任务启用 `recovery_policy_version=bounded-recovery-v1`，旧任务保留原协议；显式重放在独立副本中升级并记录来源。需求清单结构、生成时机、独立上下文、Docker 隔离和所有客观质量门禁保持原定义。本轮不调整规避资产及其门禁。

正常标准审查拒绝规则候选时，服务端提供可纠正字段路径并按实际路径决定资产所有者：replacement_rules 回到清单复核，objective 回到规范审查，公开接口问题进入现有独立接口提案复核。未知位置返回具体合法路径，不能静默退回整包重建。局部修订上下文保留原质疑和完整拒绝意见。清单复核若发现接口确实不足，可以返回 InterfaceReturn 提案；提案尚未授权修改接口，仍经原接口复核。规则用于选择覆盖样例，不对所有合法输入增加条件。 InterfaceReturn只需为受影响的被质疑需求提交接口提案，其余质疑保留为后续覆盖复核的历史依据，不自动认可或强迫它们一起改接口。采纳审查发现接口问题时先退回创建阶段提出具体需求提案，服务端不替模型虚构所有需求的接口缺项。

公开规范补充每批最多四次，同一字段范围最多两次；相同资产重复应用不重复扣次，重复候选与相同问题停止。计数持久化，不因换措辞、规范哈希变化、刷新或重启重置。已有局部补丁调用上限和总预算仍生效。规范审查优先检查核心正常行为，再检查字段取值细节。公开 input_schema/output_schema 的 description 加入逐字引用来源；这仅证明引用存在，语义是否充分、与其他公开规则是否矛盾仍须模型审查。 正常标准审查还允许逐字引用candidate/current_public_specification单个解码后字符串字段，避免JSON转义误拒；跨字段拼接或原始需求非连续引用仍拒绝。

`output_limit` 单独恢复，不占用业务修订次数：同一阶段与资产依据最多重试一次，重建当前上下文并移除重复的错误历史，不采纳截断正文。重试输出额度最多为基础阶段额度两倍、单次不超过 48000 Token，仍受原批次请求、输入、输出和时间预算限制。记录前次调用 ID、实际输入字节和供应商元数据；未知 usage 按原保守记账。不降低 reasoning 配置，不重跑已经完成的阶段。第二次耗尽明确标记 output_limit，不能当作项目行为不合格。已成功完成的调用在恢复时继续复用已有资产。

## lean-generation-v1（2026-10-21 新建默认）

新 API 记录使用精简流程：故障项目构建 → 简短规范审核 → 独立行为测试 → 一次覆盖复查 → 故障复现检查 → Docker 故障验收 → 修复补丁及验收 → 规避和最终矩阵 → 教学 → 作者审核。覆盖修复后只复查当前测试，不再运行需求清单 DSL、清单生成/补齐/质疑/接口提案复核或正常标准重复采纳调用。旧记录保留原版本及原资产，不自动迁移。

`generation_lean.py` 提供短审核 schema。规范审核不要求模型抄哈希、逐输出字段给引文或编写清单；仅阻塞核心需求偏离、正常/故障标准混淆、必要场景不可表达和正确结果不可确定的矛盾。覆盖复查输入为原始需求、公开规范及具体 input/expected，不含实现、私有设计、实际输出。通过仅为模型意见，不能声称穷尽原需求或代码已经通过。

覆盖决定为 approve / add_tests / specification_issue。补测试仍使用已有 base_hash/added_cases 协议，程序原样合并旧输入、期望、可见性、覆盖和规避要求，只有成功保存后才清理追加状态。接口需改变时直接向构建阶段交接具体字段与问题，并生成新规范/项目版本；普通公开文字补丁保留故障代码和私有设计。受影响评测重新生成。规范/补测每类最多两次，旧指纹补测出口另有原两次限制；均服从同一总请求/时间/Token预算。普通恢复不清零，显式授权新预算子记录重置批次计数，父记录不变。

协议标记独立于 demand_coverage/safeguards。程序保留工单纠错、一次输出耗尽恢复、具体错误反馈、镜像/资产绑定和执行门禁；无需开启旧清单协议来获得通用恢复。审批绑定规范、原始需求/回答和当前测试摘要，执行及发布重新检查；旧审核不能证明新资产。普通界面展示覆盖意见及其限制，作者资产保留完整历史。人工批准仍是独立发布步骤。
